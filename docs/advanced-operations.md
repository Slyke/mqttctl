# Advanced Operations

This guide documents the implementation that is checked into the repo today.

## Runtime Inputs and Restart Rules

- The control plane reads:
  - `MQTTCTL_CONFIG_PATH`
  - `MQTTCTL_SECRETS_PATH`
- The broker-agent reads:
  - `MQTTCTL_BROKER_AGENT_CONFIG_PATH`
- Those JSON files are bootstrap-only:
  - the app never rewrites them
  - you must restart the process after changing them
- SQLite is the default DB mode:
  - `MQTTCTL_DB_KIND=sqlite`
  - `MQTTCTL_SQLITE_PATH=/path/to/mqttctl.sqlite`
- Postgres mode requires:
  - `MQTTCTL_DB_KIND=postgres`
  - `config.database.postgres`
  - `secrets.postgresPassword`

## HTTP API Routing

- `config.httpApi.mode` defaults to `browser`
- browser mode keeps the existing browser-facing API prefix at `config.httpApi.browserBasePath`, defaulting to `/api`
- proxy mode changes browser HTTP API calls to `config.httpApi.proxy.basePath`, such as `/api-proxy`, and the SvelteKit Node process forwards those requests to `config.httpApi.proxy.upstreamBaseUrl`
- proxy mode requires `config.httpApi.proxy.upstreamBaseUrl`
- `config.httpApi.proxy.upstreamBasePath` defaults to `/api`, so `/api-proxy/dynsec/clients` forwards to `{upstreamBaseUrl}/api/dynsec/clients`
- proxy mode applies to browser HTTP API requests, including the MQTT Explorer SSE stream, but not websocket upgrades. The dashboard websocket still connects to `{basePath}/api/dashboard/ws`, so any reverse proxy in front of the UI must continue to route websocket upgrades for that path.

## Control Plane vs Broker-Agent Boundary

- If `config.broker.agent.baseUrl` is unset, the control plane:
  - reads and writes the configured broker config file directly
  - reads the dynsec state file directly
  - runs `mosquitto_ctrl` locally for dynsec commands
  - uses `broker.reloadCommand` and `broker.restartCommand` for lifecycle actions
- If `config.broker.agent.baseUrl` is set, the control plane moves those operations to broker-agent:
  - broker config read and write
  - reload and restart
  - dynsec state reads
  - dynsec commands
  - managed key-file listing and downloads

Important details:

- `broker.agent.baseUrl` may include a path prefix; the client preserves it when constructing requests
- `broker.agent.insecure` only disables TLS verification for the app-to-agent HTTPS hop
- broker-agent `/health` and `/healthz` do not require the shared API key
- all other broker-agent endpoints require `x-api-key`
- broker-agent `listen.http.host` and `listen.https.host` must be IP addresses, not DNS names
- if the dynsec state file is missing and `broker.dynsecBootstrap` is configured, broker-agent initializes it with `mosquitto_ctrl dynsec init`

## Auth Modes

### Local Auth

- local auth can be enabled by itself or alongside OIDC or trusted-header auth
- usernames are canonicalized to lowercase
- on first run, the app creates a protected local `super_admin`
- if `secrets.bootstrapAdmin.password` is missing, a one-time random password is generated and printed to console with `#####` delimiters
- autogenerated bootstrap credentials are not written to file log sinks
- password resets and disable or enable controls apply only to local accounts
- resetting a local password or disabling a local account invalidates that user’s sessions by bumping `sessionVersion`

### OIDC

- OIDC defaults its callback URL to `{publicBaseUrl}{basePath}/auth/callback`
- `auth.oidc.callbackUrl` can override that value
- `auth.oidc.tokenEndpointAuthMethod` defaults to `client_secret_post`
- discovery can be overridden with explicit authorization, token, and userinfo endpoints
- successful OIDC login first matches by `external_subject`, then by lowercase username
- when a username match is auto-linked:
  - the user keeps the existing role
  - any local password hash is cleared
  - the local disabled flag is cleared
  - sessions are invalidated by bumping `sessionVersion`
- protected local accounts are not auto-linked
- `auth.oidc.bootstrapAdminSubject` creates the first matching OIDC user as `super_admin`; all other new OIDC users start as `viewer`

### Trusted Header Auth

- trusted-header auth is disabled unless `auth.headerEnabled` is `true`
- it is mutually exclusive with OIDC
- the app trusts only source IPs inside `auth.header.trustedCidrs`
- the app checks `auth.header.requiredHeaders` before accepting the login
- the username comes from `auth.header.usernameHeader`
- new trusted-header users are created with `auth.header.defaultRole`
- current implementation note:
  - `auth.header.groupsHeader` is accepted in config and logged at startup
  - it is not currently mapped onto app roles or permissions
- like OIDC auto-linking, trusted-header auto-linking clears any stored local password and disabled state unless the account is protected from auto-linking

## DynSec

The app works with raw Mosquitto dynsec concepts. The ACL types exposed in the UI and API are:

- `publishClientSend`
- `publishClientReceive`
- `subscribeLiteral`
- `subscribePattern`
- `unsubscribeLiteral`
- `unsubscribePattern`

Current behavior:

- the role API supports batch ACL adds through `acltypes`
- assignment priorities exist on client-group and role-assignment edges
- the page hides assignment priorities unless `config.ui.dynsec.showAssignmentPriorities` is enabled
- DynSec labels can be overridden with `config.ui.languageFilePath`

### Default Client Role Bootstrap

On startup the control plane may bootstrap app-owned DynSec roles:

- it happens only when broker state still looks like initial bootstrap state
- it creates `read-all` as the default role for new clients
- it creates `read-write-all` as an additional non-default bootstrap role that remains available in the role list
- it is a one-time bootstrap, not an ongoing repair loop for arbitrary operator-defined roles
- if an older bad state stored `mqttctl-default`, startup migrates that legacy role to `read-write-all`
- if the configured default role later disappears, new client creation fails with a clear error instead of silently recreating it automatically
- the dashboard exposes bootstrap status as `idle`, `running`, or `failed`
- the DynSec page suppresses the stale missing-role warning for `read-all` while bootstrap is still running or has just failed

## MQTT Config Page

Role behavior:

- any authenticated user can view managed key-file status and download configured public artifacts
- only `broker_admin` and `super_admin` can pull raw broker config text, push changes, reload, or restart

Config editing behavior:

- the page edits the raw text at `config.broker.mainConfigPath`
- pushes are conflict-checked against the last pulled text
- a push does not auto-reload or auto-restart the broker
- push, reload, and restart are serialized through the in-process job queue

Managed key-file behavior:

- only these symbolic IDs exist:
  - `caFile`
  - `mosquittoPublicKey`
  - `brokerPublicKey`
- private keys are never exposed
- if broker-agent is enabled but does not implement `/broker-key-files`, the control plane falls back to reporting configured metadata from its own config JSON

## Dashboard and Health

The dashboard exposes both page-load data and API data, plus a live websocket feed:

- server-rendered page load uses the same dashboard data service as `GET /api/dashboard`
- API consumers can read the current dashboard payload from `GET /api/dashboard`
- live updates: websocket upgrade on `/api/dashboard/ws`

Current diagnostics summary includes:

- broker reachability
- dynsec state readability
- dynsec bootstrap status
- broker config readability
- last reload status
- last restart status

Current dashboard view also shows:

- WUI-to-API transport security
- API-to-broker-agent or API-to-broker transport security
- broker-agent-to-Mosquitto transport security when broker-agent mode is enabled
- recent audit entries if the user can view audit history
- user counts, plus client, group, and role counts when DynSec is readable and not still bootstrapping

## Audit History

The audit page:

- remains append-only from the UI perspective
- records write actions, successful control-plane startup, and successful or failed local or OIDC login outcomes
- lets operators switch between the latest `10`, `20`, `50`, `100`, or `all` entries
- exports the currently selected latest-entry slice as JSON

Audit export details:

- the export includes export time, build label, and the applied latest-entry index filter
- each exported entry includes the previous entry hash
- the export includes a SHA-256 integrity summary for the full audit chain
- operators can recompute an entry hash from the exported JSON entry object and compare it with the chain metadata to spot tampering

The dashboard websocket enforces:

- the configured `basePath`
- same-origin checks against `publicBaseUrl`
- session-cookie auth or trusted-header auth
- the normal `read` capability check

## MQTT Explorer

The MQTT explorer is browser-session scoped:

- the backend keys each explorer session by `app-user-id + mqttctl_mqtt_browser_session cookie`
- live updates use Server-Sent Events on `/api/mqtt/events`
- when the browser live channel closes, the backend waits 10 seconds before disconnecting and deleting the MQTT session

Current credential modes exposed by the page:

- `dynsec_client`
- `custom`

Details:

- `dynsec_client` mode requires `manage_broker`
- if the chosen dynsec username matches the configured dynsec admin username and no password is supplied, the backend reuses the configured admin password
- custom mode requires a username, password, and client ID
- TLS in the explorer is transport-only right now:
  - the page lets you toggle MQTT vs MQTT TLS
  - certificate verification is disabled in the current implementation
  - there is no CA, client cert, or key upload flow in the UI
- for dynsec clients, the page shows a single helper list derived from effective `subscribe*` ACLs
- the page may still warn when separate receive or publish ACLs can make message tests fail even though a helper filter looks broad

Latest-topic behavior:

- the explorer stores only the latest payload per topic
- the page can clear that in-memory view
- the page can set the tracked-topic limit to:
  - `5`
  - `10`
  - `20`
  - `25`
  - `100`
  - `null` for all tracked topics
- the backend still enforces an absolute cap of `500` tracked topics per session

## Snapshots

Current export kinds:

- `dynsec`
- `broker-config`
- `combined`

Current import behavior:

- snapshot exports use the same top-level envelope style as audit exports, including `title`, `type`, `exportTime`, and `build`
- preview accepts exported snapshot JSON payloads
- apply currently pushes `data.brokerConfig.current` when that value is present
- dynsec payloads are preview-only during import because client passwords are not exported or restored
- combined apply does not recreate app users or dynsec state
- snapshot history stores metadata and payloads in the application DB

## Logging Overrides

The control plane supports deploy-time sink overrides on top of config JSON:

- console:
  - `MQTTCTL_LOG_CONSOLE_ENABLED`
  - `MQTTCTL_LOG_CONSOLE_LEVELS`
  - `MQTTCTL_LOG_CONSOLE_FORMAT`
- file:
  - `MQTTCTL_LOG_FILE_ENABLED`
  - `MQTTCTL_LOG_FILE_LEVELS`
  - `MQTTCTL_LOG_FILE_FORMAT`
  - `MQTTCTL_LOG_FILE_PATH`
- curl:
  - `MQTTCTL_LOG_CURL_ENABLED`
  - `MQTTCTL_LOG_CURL_LEVELS`
  - `MQTTCTL_LOG_CURL_METHOD`
  - `MQTTCTL_LOG_CURL_TIMEOUT_MS`
  - `MQTTCTL_LOG_CURL_URL`

The control plane also accepts `MQTTCTL_LOG_HTTP_*` aliases for the curl sink.

Kubernetes metadata injection for logs is also available:

- enable it with either `MQTTCTL_LOG_K8S_METADATA_ENABLED=true` or the styleguide-compatible `LOG_K8S_METADATA_ENABLED=true`
- provide any metadata values you want attached to each log entry:
  - `K8S_POD_NAME`
  - `K8S_DEPLOYMENT`
  - `K8S_NAMESPACE`
  - `K8S_POD_IP`
  - `K8S_POD_IPS`
  - `K8S_NODE_NAME`
- the control plane also accepts the same defaults in config JSON under `logging.kubernetes.*`
- when enabled, JSON logs include a `kubernetes` object and text logs append `| kubernetes=...`

Broker-agent logging is still console-oriented:

- `MQTTCTL_LOG_CONSOLE_FORMAT=json` switches broker-agent console output from text to JSON
- the broker-agent also reads `MQTTCTL_LOG_K8S_METADATA_ENABLED` or `LOG_K8S_METADATA_ENABLED` plus the same `K8S_*` metadata env vars and attaches that metadata to each log entry when enabled
